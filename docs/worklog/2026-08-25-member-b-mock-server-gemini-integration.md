## 1. 구현 — 병합 계약으로 Mock 서버 재건

## 2. 모델 조사 — TODO의 "Gemini 1.5 Flash"는 실행 불가능한 계획이었다

- **막힘** — `gemini-1.5-flash`는 이미 서비스 종료(2025-09-29). `gemini-2.0-*` 계열도 2026-06-01 종료. TODO에 적힌 모델은 존재하지 않는 것이었다.
- **발견** — Computer Use는 우리 구조에 안 맞음. 입력이 스크린샷 전용이라 접근성 트리를 못 받고, **금융 거래에 사용자 확인을 요구하는 내장 정책**이 있어 "결제까지 무중단"과 정면 충돌했다.

## 3. Gemini 연동 — 문서와 실제가 세 번 어긋났다

"Gemini API로 구현해줘"부터 실제로 응답이 오기까지, 공식 문서를 그대로 믿었으면 몰랐을 실패가 세 개 있었다.

- **막힘 ①** — `client.interactions.create`가 150초 무응답. 공식 문서가 권장하는 최신 API였다. TCP·TLS·요청 전송까지 정상인데 서버가 응답 헤더를 아예 안 보냈다. 같은 키·모델로 legacy `generateContent`는 2초대에 정상 응답 — 그쪽으로 전환.
- **막힘 ②** — HTTP deadline 4.5초 → 전 요청 `400`. `Minimum allowed deadline is 10s.` 게다가 `http_options.timeout`은 **밀리초** 단위라 초 단위로 넣으면 타임아웃이 사실상 사라진다. 10초 하한 + clamp 로직을 넣고, 라우터 타임아웃을 12초로 올려 SDK 쪽이 먼저 끊기게 했다.
- **막힘 ③** — 벤치마킹 중 무료 티어 할당량(20회/일) 소진. 사용자가 "422 오류"로 신고한 것의 실제 원인 — 옛 프로세스가 포트를 잡은 채 낡은 설정을 캐시하고 있었던 것과 겹쳐 진단이 두 겹이었다.

> 이 단계 끝: 49 tests, 실제 엔드투엔드 4개 시나리오 검증 (CLICK / SET_TEXT / 결제 화면 비차단 / 거절)

## 5. 시나리오 전환 — 코레일+ 예매에서 카카오톡 사진 전송으로

"결정론적 슬롯 검사가 필요할까?"라는 질문에, 코드를 짜기 전에 먼저 재봤다.

- **발견** — KTX 전용 프롬프트로도 카카오톡 판단은 이미 절반쯤 맞았다. 시스템 프롬프트에 출발역·좌석등급 같은 KTX 슬롯명이 박혀 있었는데도, 3회 중 2회는 김엄마/엄마♥를 구분해 되물었다. 원칙 자체는 일반화되어 있었다는 뜻.
- **결정** — 서버 코드 대신 프롬프트 규칙 한 줄. "후보가 여럿이면 반드시 되물으세요"를 프롬프트 v2에 추가. 모호한 목표 되묻기 **67% → 100%**(5/5), 명확한 목표도 5/5 정확(과잉 되묻기 없음). 계획했던 결정론적 슬롯 검사 코드는 불필요해졌다.

**위험의 종류가 바뀌었다.** 잘못된 기차표는 수수료를 내고 취소할 수 있었다. 잘못 전송된 사진은 되돌릴 방법이 없고 사생활 침해 성격이 있다 — 금전 손실이 사라졌다고 안전해진 게 아니라는 점을 CLAUDE.md·모든 기획 문서에 핵심 리스크로 다시 썼다.
