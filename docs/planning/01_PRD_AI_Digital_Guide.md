# PRD — 음성 앱 대행 에이전트

어르신·디지털 취약계층이 "앱을 찾아 열고 조작하는 일" 자체를 없애는 Android 음성 자동화 서비스

UNWORK Hackathon · 2026.08

# 개요

## 한 줄 정의

| **한 줄 정의** 어르신이 앱 하나만 켜고 말하면, AI가 알맞은 앱을 스스로 찾아 열고 목표를 끝까지 수행하는 Android 접근성 레이어. 되돌릴 수 없는 행동(결제·전송·삭제) 직전에만 구두로 동의를 구하고, 동의를 받으면 그 버튼까지 AI가 직접 누른다. |
| --- |

## 제품 목표

사용자가 앱을 직접 찾아 열고 메뉴를 조작하는 선행 작업(앱 탐색, 단계별 입력)을 전부 없앤다.

**대상 앱을 고정하지 않는다.** 사용자가 무엇을 말하든 AI가 설치된 앱 중에서 적절한 앱을 골라 실행하는 것이 제품의 본질이다. 특정 앱 전용 매크로가 아니다.

자녀·보호자가 대신 조작해주거나 반복 설명하는 시간을 없앤다.

기존 앱을 수정하지 않아도 Android 접근성 레이어 위에서 동작하는 MVP를 만든다.

해커톤에서는 카카오톡 사진 전송 시나리오 1개에서 발화→완료까지 end-to-end 성공을 목표로 한다.

## 배경

기존 '말하면 척척'(fluiz 기반, 서울AI재단 공동개발)은 음성 제어를 지원하지만 사용자가 앱을 직접 찾아 열고 서비스를 실행해야 하는 선행 UX Work가 남아있다. Gemini Live·손주도움 같은 서비스는 "무엇을 눌러야 하는지 알려주는" 안내형이며 조작은 여전히 사용자 몫이다.

UNWORK 관점에서 지워야 할 것은 **앱을 찾고 메뉴를 눌러가는 조작 노동**이다. 이 프로젝트는 안내가 아니라 대행을 한다. 사람은 처음 목적을 말하는 것, AI가 되물을 때 답하는 것, 되돌릴 수 없는 행동에 동의하는 것만 한다.

[도식 1] 발화 이후 목표 완료까지 전 과정을 자동화

# 문제 및 해결 방안

## 사용자 문제

어떤 앱을 열어야 하는지부터 막힌다. 앱 아이콘이 수십 개인데 이름과 기능이 매칭되지 않는다.

앱을 열어도 메뉴 구조를 몰라 원하는 기능까지 도달하지 못한다. 사진 한 장 보내는 데 5~6단계를 거쳐야 한다.

앱이 업데이트되어 UI가 바뀌면 이전에 외운 순서가 무용지물이 된다.

결과적으로 자녀에게 부탁하게 되고, 자녀는 같은 작업을 반복 대행하며 시간·감정 소모가 발생한다.

## 해결 방안

사용자가 우리 앱을 실행하고 마이크를 눌러 목적을 말한다. 예: "영희한테 카톡으로 방금 찍은 사진 보내줘."

AI가 **설치된 앱 목록을 보고 어떤 앱을 열지 스스로 판단**해 실행한다. 사용자가 앱 이름을 정확히 말하지 않아도 된다.

AccessibilityService가 현재 화면의 UI text, contentDescription, 클릭 가능 여부, 입력 가능 여부, 화면 좌표 등을 읽는다.

AI 에이전트가 사용자 목표와 현재 UI 목록을 보고 다음에 실행할 것 하나를 판단해 `performAction(ACTION_CLICK)` 또는 `ACTION_SET_TEXT`로 직접 실행한다. 화면이 바뀌면 이를 반복한다.

첫 발화가 "카톡 보내줘"처럼 받는 사람·보낼 내용을 다 담고 있지 않으면(오히려 이 경우가 기본), AI가 해당 화면 단계에서 부족한 정보를 되묻고 답변을 반영해 이어서 진행한다.

**결제·전송·삭제처럼 되돌릴 수 없는 행동 직전에는 반드시 구두로 확인한다.** "영희님께 사진을 보낼까요?" — 사용자가 "응"이라고 답하면 AI가 그 버튼을 누른다.

[도식 2] 발화 → 앱 자동 선택 → 자동 진행 → 구두 동의 → 완료

## 차별점

| **기준** | **기존 방식** | **우리 제품** |
| --- | --- | --- |
| 앱 선택 | 사용자가 앱을 찾아 직접 실행 | AI가 목표를 보고 설치된 앱 중에서 선택·실행 |
| 행동 주체 | 사용자가 화면을 보고 직접 조작 | AI가 UI 노드를 직접 클릭·입력 |
| 핵심 가치 | 대화형 안내 또는 부분적 음성 제어 | 앱 탐색·조작 노동 자체를 제거 |
| 화면 이해 | 화면 공유·카메라 또는 사용자 직접 조작 | Accessibility UI Tree 우선, Vision은 보조 |
| 안전 경계 | 전 과정 위임 또는 전 과정 사용자 조작 | 되돌릴 수 있는 행동은 자동, 되돌릴 수 없는 행동만 구두 동의 |
| 적용 범위 | 특정 앱/특정 시나리오 전용 | 앱 비종속 — 접근성 정보가 노출되는 앱이면 동작 |

## 결제·되돌릴 수 없는 행동의 연동 범위 (In-Scope / Out-of-Scope)

결제·송금·전송·삭제는 **하나의 동일한 메커니즘**으로 처리한다 — 구두 동의 게이트(`CONFIRM_REQUIRED`). 결제만 특별 취급하는 별도 코드 경로가 없다.

| **구분** | **범위** |
| --- | --- |
| In-Scope | 대상 앱에 사용자가 사전 등록해 둔 실제 결제수단으로 그 앱 자체의 결제가 완료되는 것. AI가 구두 동의를 받은 뒤 결제 확정 버튼까지 accessibility 자동 클릭으로 실행한다. |
| Out-of-Scope | 우리 backend/Android가 PG사 API를 직접 호출하는 별도 결제 연동을 새로 구축하는 것. 결제는 대상 앱이 이미 갖고 있는 결제 흐름을 그대로 자동 조작하는 방식이며, 우리 시스템이 결제망에 직접 연결되지는 않는다. |

**해커톤 데모에서는 실제 결제를 하지 않는다.** 카카오톡 "전송" 버튼이 결제 버튼과 코드상 완전히 같은 경로를 타므로, 실제 금전을 쓰지 않고도 결제 동의 UX를 그대로 시연할 수 있다. 발표에서 이 점을 명확히 말한다 — "결제도 이것과 같은 코드로 동작합니다."

# 타겟 및 시나리오

## 타겟 사용자

Primary: 앱 조작 자체가 부담스러운 60대 이상 사용자.

Secondary: 부모의 스마트폰 조작을 대신 해주던 자녀·보호자.

확장 타겟: 디지털 초보자, 인지·학습상의 어려움이 있는 사용자, 시각 제약이 있는 사용자, 손을 쓰기 어려운 상황의 일반 사용자.

MVP 타겟 환경: Android 실기기 + 사용자의 기기에 이미 설치된 앱.

## 사용자 시나리오

**대표 시나리오 — 카카오톡 사진 전송 (해커톤 데모)**

사용자가 우리 앱을 실행하고 마이크를 눌러 "영희한테 카톡으로 방금 찍은 사진 보내줘"라고 말한다.

AI가 설치된 앱 목록에서 카카오톡을 골라 실행한다.

친구 검색 → "영희" 입력 → 검색 결과 선택 → 대화방 진입까지 자동 진행한다.

사진 첨부 → 앨범 → 가장 최근 사진 선택까지 자동 진행한다.

전송 버튼 차례에서 AI가 멈추고 "영희님께 사진을 보낼까요?"라고 음성으로 묻는다.

사용자가 "응"이라고 답하면 AI가 전송 버튼을 눌러 실제로 전송한다. "영희님께 사진을 보냈어요."

[도식 4] 발화 한 번으로 앱 선택부터 전송까지, 동의는 마지막 한 번

**보조 시나리오 — 정보가 부족한 발화("카톡 보내줘")**

사용자가 "카톡 보내줘"라고만 말한다 — 받는 사람도 보낼 내용도 없음.

AI가 카카오톡을 실행하지만, 지금 화면에서 무엇을 눌러야 할지 확정할 정보가 없다고 판단해 자동 클릭을 멈추고 "누구에게 보낼까요?"라고 되묻는다.

사용자가 "영희요"라고 답하면 AI가 이어서 "무엇을 보낼까요?"를 묻고, "아까 찍은 사진"이라고 답하면 사진 첨부 흐름으로 진행한다.

필요한 정보가 채워진 이후부터는 대표 시나리오와 동일하게 자동 진행하며, 전송 직전에 동의를 구한다.

[도식 4-1] 정보가 부족한 발화에서 단계별로 되물어 채워나가는 흐름

**확장 시나리오 — 결제 (데모 이후)**

"내일 아침 서울에서 부산 가는 기차표 예매해줘" → AI가 코레일+를 실행하고 출발역·도착역·날짜·좌석을 진행 → 결제 버튼 앞에서 "총 59,800원을 결제할까요?" → "응" → 결제 확정.

이 시나리오는 대표 시나리오와 **완전히 같은 코드 경로**를 탄다. 앱 이름도 버튼 이름도 코드에 없다.

# 성공·위험 요소

## 핵심 지표

| **지표** | **정의** | **MVP 목표** |
| --- | --- | --- |
| Task Success Rate | 발화부터 목표 완료까지 중단 없이 도달한 비율 | 80%+ |
| App Selection Accuracy | AI가 목표에 맞는 앱을 골라 실행한 비율 | 95%+ |
| Next-Step Accuracy | AI가 선택한 다음 UI가 실제 올바른 경로였던 비율 | 90%+ |
| Clarification Accuracy | 정보가 부족할 때 AI가 실제로 물어야 할 항목을 정확히 짚어 질문한 비율 | 90%+ |
| Confirmation Recall | 되돌릴 수 없는 행동 직전에 실제로 동의를 구한 비율 | **100%** (누락은 곧 사고) |
| Time to Complete | 목적 발화부터 목표 완료까지 걸리는 시간 | 60초 이내 |
| Correct-Target Rate | 사용자가 말한 대상(받는 사람/금액/일정)과 실제 실행 결과가 일치한 비율 | 100% |

## 리스크

| **리스크** | **왜 발생하는가** | **대응** |
| --- | --- | --- |
| AI 오판으로 엉뚱한 상대에게 전송/결제 | 목표 해석과 UI 의미 연결 오류. 되돌릴 수 없는 행동은 오판이 곧 실제 피해 | 되돌릴 수 없는 행동은 LLM 판단과 서버 키워드 게이트로 2단 방어. 확인 문장에 상대방·금액을 반드시 포함해 사용자가 틀린 것을 알아챌 수 있게 함 |
| LLM이 확인 단계를 건너뜀 | 프롬프트만으로는 100% 보장 불가 | 서버가 `IRREVERSIBLE_KEYWORDS`로 독립 검사해 강제 override. 프롬프트 하나에 안전을 걸지 않음 |
| Play 정책 위반 | Accessibility API로 여러 단계를 자율 실행하는 것은 Play의 "자율적 계획·실행 자동화 제한" 조항에 저촉될 소지 | 접근성 목적(디지털 취약계층 지원)을 정책 심사에서 명확히 소명. 보안 통제 우회를 하지 않음을 명시 |
| 대상 앱의 접근성 정보 부족 | 아이콘에 contentDescription이 없거나 커스텀 렌더링(이미지 그리드 등)이면 텍스트 노드가 없음 | Screenshot + Vision fallback. 사진 그리드가 대표적 위험 지점이므로 데모 전 반드시 실기기 확인 |
| 앱 업데이트로 UI 변경 | 앱이 개편되면 화면 구조가 달라짐 | UI Tree를 매 스텝 새로 읽는 구조라 순서를 외우지 않음 — 원리적으로 내성이 있으나 실측 필요 |
| 대화 내용 프라이버시 | 메시지 앱 화면에는 사적인 대화가 그대로 노출됨 | UI Tree 비영속화(추론 직후 폐기), 로그에 text/contentDescription 원문 미기록, 비밀번호 필드·주민번호·카드번호 패턴 서버단 마스킹 |
| 음성 인식 실패 (사투리·노인성 발음) | STT 정확도가 고령 화자에서 떨어짐 | 되묻기 UX가 곧 복구 경로. 인식 결과를 화면에도 크게 표시해 사용자가 오인식을 확인 가능하게 함 |

[도식 5] 되돌릴 수 없는 행동 자동화에 따른 신뢰·정책·프라이버시 리스크 관리

| **항목** | **설정** |
| --- | --- |
| 제품 분류 | Voice Automation / AI Agent / Digital Inclusion |
| 플랫폼 | Android Mobile |
| 핵심 상호작용 | 앱 실행 → 음성 목표 입력 → AI 앱 선택·자동 실행 → (부족한 정보는 단계마다 되물음) → 되돌릴 수 없는 행동은 구두 동의 → 완료 |

Android에서 화면 공유를 켜고 다른 앱을 사용하면서 Live 대화를 계속할 수 있음. 화면에 대한 실시간 도움을 제공.

**[S3] 손주도움 - Google Play**
https://play.google.com/store/apps/details?id=com.guideops.app
스마트폰 화면·키오스크·약봉투 등을 카메라로 비추면 다음 버튼과 사용법을 음성 안내.

**[S4] Android AccessibilityService API**
https://developer.android.com/reference/android/accessibilityservice/AccessibilityService
접근성 서비스는 UI 이벤트를 받고 활성 창의 UI 트리를 조회할 수 있으며 접근성 오버레이를 그릴 수 있음.

**[S5] Android AccessibilityNodeInfo API**
https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo
UI 노드의 text, contentDescription, boundsInScreen, isEditable, isPassword 등 접근성 정보를 조회하고 ACTION_CLICK·ACTION_SET_TEXT 등을 수행할 수 있음.

**[S6] Google Play AccessibilityService 정책**
https://support.google.com/googleplay/android-developer/answer/10964491?hl=ko
접근성 API 사용 시 선언·공개·동의 요구. 일반 앱의 자율적 계획·실행 자동화는 제한되며 장애 지원이 핵심인 접근성 도구는 별도 기준 적용.

**[S7] Google Play 민감 권한/API 정책**
https://support.google.com/googleplay/android-developer/answer/16558241
Accessibility API는 보안 통제 우회·기만적 UI 조작 등에 사용할 수 없고 목적에 필요한 최소 데이터만 처리해야 함.

**[S8] Android 패키지 가시성 (`<queries>`)**
https://developer.android.com/training/package-visibility
Android 11(API 30) 이상에서는 Manifest에 `<queries>`를 선언하지 않으면 다른 앱의 설치 여부를 조회할 수 없음. AI가 설치된 앱 중에서 대상 앱을 고르는 구조상 필수 선언.

**[S9] 디지털정보격차 실태조사 (과학기술정보통신부·한국지능정보사회진흥원)**
고령층의 디지털 접근·역량·활용 수준을 매년 조사하는 국가승인통계. 발표에서 수치를 인용할 경우 최신 연도 보고서 원문을 직접 확인해 인용할 것 — 이 문서에는 수치를 적어두지 않는다.
