# PRD — 화면 Off 음성 자동예매 에이전트

어르신·디지털 취약계층이 "앱을 찾아 열고 조작하는 일" 자체를 없애는 Android 음성 자동화 서비스

UNWORK Hackathon · 2026.08

# 개요

## 한 줄 정의

| **한 줄 정의** 화면이 꺼진 상태에서 사용자가 음성으로 목적을 말하면, AI가 대상 앱을 스스로 실행해 목적지·시간·좌석 선택은 물론 결제까지 중단 없이 자동으로 완료하는 레이어. |
| --- |

## 제품 목표

사용자가 앱을 직접 찾아 열고 메뉴를 조작하는 선행 작업(화면 On, 앱 탐색, 단계별 입력)을 전부 없앤다.

자녀·보호자가 예매를 대신 해주거나 반복 설명하는 시간을 없앤다.

AI는 목적지·시간·좌석 선택은 물론 결제까지 스스로 진행한다. 결제는 Mock이 아니라 코레일+ 앱에 사전 등록된 실제 결제수단으로 그 앱의 실제 결제 화면을 그대로 자동 실행하며, 실제 금전이 이동한다.

기존 앱을 수정하지 않아도 Android 접근성 레이어 위에서 동작하는 MVP를 만든다.

해커톤에서는 코레일+ 앱의 KTX 예매 시나리오 1개에서 화면 Off 음성 호출→결제 도달까지 end-to-end 성공을 목표로 한다.

## 배경

기존 '말하면 척척'(fluiz 기반, 서울AI재단 공동개발)은 음성 제어를 지원하지만 사용자가 앱을 직접 찾아 열고 서비스를 실행해야 하는 선행 UX Work가 남아있다. 이 프로젝트는 이 선행 작업 자체를 제거하는 데 집중한다: 화면이 꺼진 상태에서도 음성 한마디로 목적이 실행 단계까지 진입하게 한다.

UNWORK 관점에서 지워야 할 것은 화면을 켜고 앱을 찾고 메뉴를 눌러가는 조작 노동이다. 결제 실행까지 AI가 실제로 대신하며, 사람은 발화 한 번으로 전체 흐름을 시작시키는 역할만 한다.

[도식 1] 발화 이후 결제 완료까지 전 과정을 자동화

# 문제 및 해결 방안

## 사용자 문제

화면을 켜고, 잠금을 풀고, 앱을 찾아 열고, 메뉴를 눌러야 예매가 시작된다.

목적지·시간·좌석 단계를 사용자가 매번 직접 입력/선택해야 한다.

명절 등 예매 경쟁 시간대에는 몇 초의 지연도 좌석 확보 실패로 이어진다.

고령자는 앱을 여는 것부터 막혀 자녀에게 예매를 부탁하는 경우가 많고, 자녀는 같은 예매를 반복 대행하며 시간·감정 소모가 발생한다.

## 해결 방안

화면 Off 상태에서도 사용자가 wake word 뒤 목적을 말한다. 예: "내일 아침 서울에서 부산 가는 KTX 예매해줘."

서비스가 코레일+ 앱을 자동 실행한다.

AccessibilityService가 현재 화면의 UI text, contentDescription, 클릭 가능 여부, 화면 좌표 등을 읽는다.

AI 에이전트가 사용자 목표와 현재 UI 목록을 보고 다음에 실행할 UI 요소를 판단해 performAction(ACTION_CLICK) 또는 setText로 직접 실행한다.

목적지·날짜·시간·좌석 선택까지 완료되면 결제까지 중단 없이 자동으로 진행한다.

결제는 코레일+ 앱에 사전 등록해 둔 실제 결제수단으로 자동 완료되며, 별도의 사용자 확인 단계를 거치지 않는다. 실제 금전이 이동한다.

[도식 2] 화면 Off 음성 호출부터 결제 완료까지 자동 진행

## 차별점

| **기준** | **기존 방식** | **우리 제품** |
| --- | --- | --- |
| 행동 주체 | 사용자가 화면을 켜고 앱을 열어 직접 조작 | 화면 Off 음성 호출만으로 목적지~좌석까지 AI가 자동 진행 |
| 핵심 가치 | 대화형 도움 또는 부분적 음성 제어 | 앱 탐색·조작 노동 자체를 제거 |
| 화면 이해 | 화면 공유·카메라 또는 사용자 직접 조작 | Accessibility UI Tree 우선, Vision은 보조 |
| 안전 철학 | 전 과정 AI 위임 | 목적지~좌석~결제까지 전 과정 자동, 실제 결제수단으로 완료 |
| UX | 앱을 열고 단계별로 조작 | 화면 Off 음성 한마디 → 결제 완료까지 자동 도달 |

[도식 3] 기존 제품 대비 포지셔닝

## 결제·예매 연동 범위 (In-Scope / Out-of-Scope)

목표는 "화면 Off 음성 호출 → 자동 진행 → 결제 완료"가 실제로 중단 없이 이어지는 것이며, 결제·예매 확정은 더미 화면이 아니라 코레일+ 앱의 실제 결제 플로우로 이루어진다. **실제 금전이 이동한다.**

| **구분** | **범위** |
| --- | --- |
| In-Scope | 코레일+ 앱에 사용자가 사전 등록해 둔 실제 결제수단으로 그 앱 자체의 예매·결제가 완료되는 것. AI가 목적지~좌석 선택에 이어 결제 확정 버튼까지 accessibility 자동 클릭으로 중단 없이 실행한다. |
| Out-of-Scope | 우리 backend/Android가 PG사 API를 직접 호출하는 별도 결제 연동을 새로 구축하는 것. 결제는 어디까지나 코레일+ 앱이 이미 갖고 있는 결제 흐름을 그대로 자동 조작해 타는 방식이며, 우리 시스템이 결제망에 직접 연결되지는 않는다. |

실제 결제가 발생하므로 반복 테스트·리허설 시 중복 결제나 매크로 탐지 리스크에 각별히 주의한다 (§리스크 참고).

# 타겟 및 시나리오

## 타겟 사용자

Primary: 예매 경쟁이 치열한 시간대 이용자, 앱 조작 자체가 부담스러운 60대 이상 사용자.

Secondary: 부모의 예매를 대신 해주던 자녀·보호자.

확장 타겟: 디지털 초보자, 인지·학습상의 어려움이 있는 사용자, 반복 조작이 번거로운 일반 사용자.

MVP 타겟 환경: Android 실기기 + 코레일+ 앱.

## 사용자 시나리오

대표 시나리오 — 서울→부산 KTX 예매

사용자가 화면이 꺼진 상태에서 "내일 아침 서울에서 부산 가는 KTX 예매해줘"라고 말한다.

서비스가 코레일+ 앱을 실행하고 출발역/도착역/날짜를 자동 입력한다.

열차 목록에서 조건에 맞는 열차를 자동 선택한다.

좌석 등급/좌석을 자동 선택한다.

결제 단계에 도달하면, 코레일+ 앱에 사전 등록해 둔 실제 결제수단으로 그 앱의 결제 화면이 자동으로 진행되고, AI가 마지막 결제 확정 버튼까지 눌러 예매를 완료한다.

이 결제는 코레일+ 앱의 실제 결제 승인 절차를 그대로 타며, 실제 금전이 이동하고 실제 예매가 확정된다.

[도식 4] 목적 발화부터 실제 결제 완료까지 중단 없는 핵심 흐름

## 리스크

| **리스크** | **왜 발생하는가** | **대응** |
| --- | --- | --- |
| 매크로 탐지 | 코레일은 반복 조회·자동 입력 패턴을 상시 모니터링하며 의심 계정을 이용 정지시킴 | 리허설·개발 단계는 목업 화면으로 최대한 검증하고, 실기기·실 계정 테스트 빈도를 최소화 |
| Play 정책 위반 | Accessibility API로 예매 앱의 여러 단계(결제 포함)를 자율 실행하는 것은 Play의 "자율적 계획·실행 자동화 제한" 조항에 저촉될 소지가 있음 | 접근성 목적(디지털 취약계층 지원)을 정책 심사에서 명확히 소명 |
| 좌석맵 접근성 정보 부족 | 좌석맵이 canvas/이미지 기반이면 텍스트 노드가 없을 수 있음 | Screenshot + Vision fallback, 좌석 등급 리스트 화면으로 대체 |
| 화면 Off 음성 상시 감지의 배터리/OS 제약 | Doze 모드·제조사 백그라운드 정책으로 서비스가 죽을 수 있음 | 배터리 최적화 예외 등록 안내, Foreground Service 유지 |
| AI 오판으로 잘못된 열차/좌석에 실제 결제 발생 | 목표 해석과 UI 의미 연결 오류. 결제까지 자동 진행되므로 오판이 곧바로 실제 금전 손실(잘못된 티켓 구매, 취소 수수료 등)로 이어질 수 있음 | 낮은 confidence면 진행 중단 후 사용자에게 확인 요청. 확인 없이 되돌릴 수 없으므로 confidence 임계값을 보수적으로 운영 |
| 중복/반복 결제 | 같은 세션이 재실행되거나 재시도 로직이 실제 결제 화면에서 다시 클릭할 경우 이중 결제가 발생할 수 있음 | 결제 확정 이후 상태를 세션에 기록해 동일 목표 재요청 시 재실행하지 않도록 방지 |

**[S6] Google Play AccessibilityService 정책**

**[S7] Google Play 민감 권한/API 정책**
https://support.google.com/googleplay/android-developer/answer/16558241
Accessibility API는 보안 통제 우회·기만적 UI 조작 등에 사용할 수 없고 목적에 필요한 최소 데이터만 처리해야 함.
