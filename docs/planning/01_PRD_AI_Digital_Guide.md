# PRD — 화면 Off 음성 자동실행 에이전트

어르신·디지털 취약계층이 "앱을 찾아 열고 조작하는 일" 자체를 없애는 Android 음성 자동화 서비스

UNWORK Hackathon · 2026.08

# 개요

## 한 줄 정의

| **한 줄 정의** 화면이 꺼진 상태에서 사용자가 음성으로 목적을 말하면, AI가 대상 앱을 스스로 실행해 대화상대·사진 선택은 물론 전송까지 중단 없이 자동으로 완료하는 레이어. |
| --- |

## 제품 목표

사용자가 앱을 직접 찾아 열고 메뉴를 조작하는 선행 작업(화면 On, 앱 탐색, 단계별 입력)을 전부 없앤다.

자녀·보호자가 대신 사진을 보내주거나 보내는 방법을 반복 설명하는 시간을 없앤다.

AI는 대화상대 선택·사진 첨부는 물론 전송 실행까지 스스로 진행한다. 사용자가 이미 로그인해 둔 카카오톡 앱의 실제 대화방에서 실제 사진이 실제 상대에게 전송된다.

기존 앱을 수정하지 않아도 Android 접근성 레이어 위에서 동작하는 MVP를 만든다.

해커톤에서는 카카오톡 앱의 사진 전송 시나리오 1개에서 화면 Off 음성 호출→전송 완료까지 end-to-end 성공을 목표로 한다.

## 배경

기존 '말하면 척척'(fluiz 기반, 서울AI재단 공동개발)은 음성 제어를 지원하지만 사용자가 앱을 직접 찾아 열고 서비스를 실행해야 하는 선행 UX Work가 남아있다. 이 프로젝트는 이 선행 작업 자체를 제거하는 데 집중한다: 화면이 꺼진 상태에서도 음성 한마디로 목적이 실행 단계까지 진입하게 한다.

UNWORK 관점에서 지워야 할 것은 화면을 켜고 앱을 찾고 메뉴를 눌러가는 조작 노동이다. 전송 실행까지 AI가 실제로 대신하며, 사람은 발화 한 번으로 전체 흐름을 시작시키고 AI가 되물을 때 답하는 역할만 한다.

[도식 1] 발화 이후 전송 완료까지 전 과정을 자동화

# 문제 및 해결 방안

## 사용자 문제

화면을 켜고, 잠금을 풀고, 앱을 찾아 열고, 대화방을 찾아야 사진 보내기가 시작된다.

사진 한 장을 보내려면 대화방 진입 → 첨부(+) → 앨범 → 사진 선택 → 전송까지 여러 단계를 거쳐야 하고, 각 단계의 아이콘 의미를 알고 있어야 한다.

연락처 목록에 비슷한 이름이 여럿 있으면(예: 김엄마 / 엄마♥ / 엄마친구아들) 대화방을 잘못 찾아 들어가기 쉽다.

고령자는 앱을 여는 것부터 막혀 자녀에게 사진 전송을 부탁하는 경우가 많고, 자녀는 같은 조작을 반복 대행하거나 반복 설명하며 시간·감정 소모가 발생한다.

## 해결 방안

화면 Off 상태에서도 사용자가 wake word 뒤 목적을 말한다. 예: "엄마한테 어제 찍은 사진 보내줘."

서비스가 카카오톡 앱을 자동 실행한다.

AccessibilityService가 현재 화면의 UI text, contentDescription, 클릭 가능 여부, 화면 좌표 등을 읽는다.

AI 에이전트가 사용자 목표와 현재 UI 목록을 보고 다음에 실행할 UI 요소를 판단해 performAction(ACTION_CLICK) 또는 setText로 직접 실행한다.

첫 발화가 "사진 보내줘"처럼 수신자·대상 사진을 다 담고 있지 않으면(오히려 이 경우가 기본), AI가 해당 화면 단계에서 부족한 정보를 되묻고 사용자의 답변을 반영해 이어서 진행한다.

수신자와 사진이 확정되면 첨부·전송까지 중단 없이 자동으로 진행한다.

수신자 후보가 여럿일 때는 자동 선택하지 않는다. 프롬프트에 "후보가 여럿이면 반드시 되물으라"는 규칙을 넣은 뒤 모호한 목표에서의 되묻기 성공률이 67% → 100%로 올라갔고, 목표가 명확한 경우에는 과잉 되묻기 없이 그대로 실행한다(실측).

[도식 2] 화면 Off 음성 호출부터 전송 완료까지 자동 진행

## 전송 실행 범위 (In-Scope / Out-of-Scope)

목표는 "화면 Off 음성 호출 → 자동 진행 → 전송 완료"가 실제로 중단 없이 이어지는 것이며, 전송은 더미 화면이 아니라 카카오톡 앱의 실제 대화방에서 이루어진다. **실제 사진이 실제 상대에게 전달되며 되돌릴 수 없다.**

| **구분** | **범위** |
| --- | --- |
| In-Scope | 사용자가 이미 로그인해 둔 카카오톡 앱에서 대화방 진입·사진 첨부·전송이 완료되는 것. AI가 대화상대~사진 선택에 이어 전송 버튼까지 accessibility 자동 클릭으로 중단 없이 실행한다. |
| Out-of-Scope | 우리 backend/Android가 카카오 메시지 전송 API를 직접 호출하는 별도 연동을 새로 구축하는 것. 전송은 어디까지나 카카오톡 앱이 이미 갖고 있는 전송 흐름을 그대로 자동 조작해 타는 방식이며, 우리 시스템이 메시지 서버에 직접 연결되지는 않는다. 카카오톡 외 메신저 지원도 이번 범위에서 제외한다. |

실제 전송이 발생하므로 반복 테스트·리허설 시 잘못된 상대에게 전송되거나 같은 사진이 중복 전송되는 리스크에 각별히 주의한다 (§리스크 참고).

# 타겟 및 시나리오

## 타겟 사용자

Primary: 앱 조작 자체가 부담스러운 60대 이상 사용자, 가족과 사진을 자주 주고받지만 단계별 조작이 어려운 사용자.

Secondary: 부모 대신 사진을 보내주거나 보내는 법을 반복 설명하던 자녀·보호자.

확장 타겟: 디지털 초보자, 인지·학습상의 어려움이 있는 사용자, 반복 조작이 번거로운 일반 사용자.

MVP 타겟 환경: Android 실기기 + 카카오톡 앱.

## 사용자 시나리오

대표 시나리오 — 카카오톡으로 엄마에게 사진 보내기

사용자가 화면이 꺼진 상태에서 "엄마한테 어제 찍은 사진 보내줘"라고 말한다.

서비스가 카카오톡 앱을 실행한다.

친구/대화 목록에서 "엄마" 대화방을 찾아 진입한다. 이때 이름이 비슷한 후보가 여럿이면 자동 선택하지 않고 되묻는다.

첨부(+) → 앨범을 눌러 사진 선택 화면으로 진입하고, 조건에 맞는 사진을 선택한다.

전송 버튼까지 AI가 눌러 사진 전송을 완료한다.

이 전송은 카카오톡의 실제 전송 흐름을 그대로 타며, 실제 사진이 실제 상대에게 도달한다.

[도식 4] 목적 발화부터 실제 전송 완료까지 중단 없는 핵심 흐름

보조 시나리오 — 정보가 부족한 발화("사진 보내줘")

사용자가 "사진 보내줘"라고만 말한다 — 수신자도, 어떤 사진인지도 없음.

서비스가 카카오톡 앱을 실행하지만, AI는 지금 화면에서 무엇을 눌러야 할지 확정할 정보가 없다고 판단해 자동 클릭을 멈추고 "누구에게 보낼까요?"라고 되묻는다.

사용자가 "엄마요"라고 답한다. 이름이 비슷한 후보(김엄마 / 엄마♥ / 엄마친구아들)가 여럿이면 후보를 읽어주고 어느 쪽인지 다시 확인한다.

대화방에 진입한 뒤 "어떤 사진을 보낼까요?"라고 되묻고, "어제 찍은 거요" 같은 답변을 받아 사진 선택 화면에서 대상을 좁힌다.

사진이 여러 장 후보로 남는 등 화면 자체가 선택을 요구하는 지점에서도 동일하게 되묻는다.

필요한 정보가 모두 채워진 이후부터는 대표 시나리오와 동일하게 전송까지 중단 없이 자동 진행한다.

[도식 4-1] 정보가 부족한 발화에서 단계별로 되물어 채워나가는 흐름

# 성공·위험 요소

## 핵심 지표

| **지표** | **정의** | **MVP 목표** |
| --- | --- | --- |
| Task Success Rate | 화면 Off 호출부터 실제 전송 완료까지 중단 없이 도달한 비율 | 80%+ |
| Next-Step Accuracy | AI가 선택한 다음 UI가 실제 올바른 경로였던 비율 | 90%+ |
| Clarification Accuracy | 정보가 부족할 때 AI가 실제로 되물어야 할 슬롯(수신자/대상 사진)을 정확히 짚어 질문한 비율 | 90%+ (프롬프트에 "후보가 여럿이면 반드시 되물으라" 규칙 적용 후 모호한 목표 기준 실측 100%) |
| Time to Wake | Wake word 인식부터 앱 실행까지 걸리는 시간 | 2초 이내 |
| Time to Send Complete | 목적 발화부터 실제 전송 완료까지 걸리는 시간 | 30초 이내 |
| Correct-Recipient Send Rate | 사용자가 말한 상대에게 실제로 전송된 비율 | 100% |

> LLM 응답 지연은 콜당 2.4초로 실측되었다. 단계 수만큼 누적되므로 Time to Send Complete 목표는 단계 수를 함께 관리해야 달성 가능하다.

## 리스크

| **리스크** | **왜 발생하는가** | **대응** |
| --- | --- | --- |
| 잘못된 상대에게 전송 (취소 불가) | 목표 해석과 UI 의미 연결 오류. 전송까지 자동 진행되므로 오판이 곧바로 회수 불가능한 결과로 이어진다. 한번 전달된 사진은 취소 수단이 없고, 내용에 따라 사생활 침해가 된다 | 낮은 confidence면 진행 중단 후 사용자에게 확인 요청. 되돌릴 수 없으므로 confidence 임계값을 보수적으로 운영 |
| 비슷한 이름의 연락처 오선택 | 김엄마 / 엄마♥ / 엄마친구아들처럼 부분 일치하는 이름이 목록에 함께 존재. **실제로 관측된 최다 오작동 원인** | 부분 일치 후보가 2개 이상이면 자동 선택 금지. 프롬프트의 "후보가 여럿이면 반드시 되물으라" 규칙으로 ASK_USER 강제(모호한 목표 되묻기 성공률 67% → 100%), 후보 이름을 읽어주고 사용자가 지목하게 함 |
| 중복 전송 | 같은 세션이 재실행되거나 재시도 로직이 전송 화면에서 다시 클릭할 경우 같은 사진이 두 번 전송될 수 있음 | 전송 완료 이후 상태를 세션에 기록해 동일 목표 재요청 시 재실행하지 않도록 방지 |
| Play 정책 위반 | Accessibility API로 메신저 앱의 여러 단계(전송 포함)를 자율 실행하는 것은 Play의 "자율적 계획·실행 자동화 제한" 조항에 저촉될 소지가 있음 | 접근성 목적(디지털 취약계층 지원)을 정책 심사에서 명확히 소명 |
| 사진 선택 화면 접근성 정보 부족 | 앨범 썸네일 그리드는 각 사진에 의미 있는 텍스트 노드가 없을 수 있음 | Screenshot + Vision fallback, "가장 최근 사진" 같은 순서 기반 지시로 대체 |
| 화면에서 읽히는 대화 내용의 프라이버시 | 대화방 진입 시 UI Tree에 이전 대화 내용·연락처가 함께 노출됨 | 요청 처리 중에만 메모리에 두고 추론 직후 폐기, 로그에 원문 미기록 |
| 화면 Off 음성 상시 감지의 배터리/OS 제약 | Doze 모드·제조사 백그라운드 정책으로 서비스가 죽을 수 있음 | 배터리 최적화 예외 등록 안내, Foreground Service 유지 |

> (팀 확인 필요) 마지막 전송 버튼 직전에 사용자 확인 단계를 한 번 둘 것인지, 후보가 모호할 때만 되묻고 나머지는 완전 자동으로 갈 것인지 팀 합의가 필요하다. 전송은 취소가 불가능하다는 점이 판단 근거가 된다.

[도식 5] 취소 불가능한 전송 자동화에 따른 신뢰·프라이버시·정책 리스크 관리
