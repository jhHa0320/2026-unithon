# 비즈니스 모델 — 음성 앱 대행 에이전트

해커톤 이후 실제 서비스로 확장할 경우의 고객, 과금, 파트너십 가설

UNWORK Hackathon · 2026.08

# 1. BM 한 줄 요약

| **BM 방향** 초기에는 **가족 구독(B2C)**으로 문제와 사용성을 검증하고, 장기적으로는 통신사·제조사·공공기관 등 **이미 시니어 고객을 갖고 있는 채널에 번들로 얹는 B2B2C**가 획득 비용과 정책 리스크를 동시에 낮추는 확장 경로다. |
| --- |

[도식] 가족 구독 검증 → 시니어 채널 번들(통신사/제조사) → 공공 디지털 포용 사업 조달

# 2. 고객과 사용자 구분

**돈을 내는 사람과 쓰는 사람이 다르다.** 이 제품의 핵심 BM 구조다.

| **구분** | **누구** | **가치** |
| --- | --- | --- |
| 직접 사용자 | 앱 조작이 부담스러운 60대 이상 | 앱을 찾고 메뉴를 누르지 않아도 목적이 달성됨 |
| **실제 구매자** | 자녀·보호자 | 반복 대행 부담 감소. "부모님께 사드리는 것"이므로 지불 의사가 사용자 본인보다 높다 |
| 채널 고객 | 통신사, 스마트폰 제조사 | 시니어 요금제·디지털 케어 상품의 차별화 기능 |
| 기관 고객 | 지자체, 복지관, 디지털 배움터 | 디지털 취약계층 지원 사업의 실행 도구 |

# 3. B2C 모델 (가족 구독)

| **플랜** | **예시 기능** | **가격 가설** |
| --- | --- | --- |
| Free | 하루 제한된 횟수의 자동 수행, 기본 앱 범위 | 무료 |
| Family | 무제한 수행, 가족 계정 연결, 자녀가 원격으로 초기 설정 지원, 지원 앱 확대 | 월 4,900~9,900원 가설 |
| Care | 중요한 동의(결제·송금) 발생 시 자녀에게 알림, 사용 리포트, 우선 지원 | 월 9,900~14,900원 가설 |

가격은 검증되지 않은 가설이다. 해커톤에서는 과금보다 **"자녀가 부모를 위해 이 기능에 돈을 낼 의사가 있는지"**를 인터뷰로 확인해야 한다. 사용자 본인이 아니라 구매자에게 물어야 한다.

# 4. B2B2C 모델

**통신사**: 시니어 요금제·디지털 케어 부가서비스에 번들. 이미 시니어 고객 명단과 과금 채널을 갖고 있어 획득 비용이 가장 낮다.

**스마트폰 제조사**: 접근성 설정 또는 기본 음성 비서에 통합. 접근성 권한 승인이 OS 차원에서 해결되는 유일한 경로이기도 하다.

**공공기관·지자체**: 디지털 배움터, 어르신 스마트폰 교육 사업의 실행 도구. 교육이 "사용법을 가르치는 것"에서 "대신 해주는 것"으로 전환.

**복지·요양기관**: 돌봄 인력의 스마트폰 대행 업무 부담 경감.

**앱 사업자**: 자사 앱의 접근성 개선 효과를 얻지만 직접 과금 대상으로는 약하다 — 우리가 그들의 앱을 조작하는 구조라 협상력이 낮다. 우선순위를 낮게 둘 것.

# 5. 수익원

| **수익원** | **과금 단위 예시** |
| --- | --- |
| 가족 구독 | 가족 계정 단위 월 구독 |

# 6. 비용 구조

**LLM inference 비용**: 화면 전환마다 1콜이 발생하는 구조라 **작업당 콜 수가 곧 원가**다. 시스템 프롬프트를 prompt caching에 올리고, effort를 낮게 유지하며, Vision fallback은 정말 필요할 때만 쓴다. 이 최적화가 곧 마진이다.

Android 앱 개발 및 QA: OS 버전·제조사·지원 앱별 테스트 비용. 앱이 업데이트될 때마다 회귀 확인이 필요하다.

접근성 권한 온보딩 지원: 어르신이 혼자 접근성 권한을 켜기 어렵다. 자녀 원격 지원 기능이 곧 CS 비용 절감 장치다.

보안/개인정보: 화면에 사적인 대화가 노출되는 구조라 데이터 최소화·감사·정책 대응 비용이 지속 발생한다.

Play 정책 대응: 접근성 목적 소명, 심사 대응 비용.

# 7. 시장 진입 전략

해커톤 데모는 실제 결제 없이 진행한다 — 전송 동의가 결제 동의와 같은 코드 경로이므로 시연에 손실이 없다.

부모-자녀 5~10쌍을 대상으로, 자녀의 대행 요청 빈도가 얼마나 줄어드는지 관찰한다. **측정 대상은 어르신의 만족도가 아니라 자녀의 시간이다** — 구매자가 자녀이기 때문이다.

접근성 권한 온보딩 성공률을 초기 최우선 지표로 둔다. 여기서 이탈하면 제품을 써보지도 못한다.

정확도와 동의 UX 신뢰가 확보된 후 통신사·제조사 채널 협상으로 확대한다.

# 8. BM의 가장 큰 리스크

| **리스크** | **영향** | **검증 방법** |
| --- | --- | --- |
| 접근성 권한 온보딩 실패 | 제품을 써보기 전에 이탈. 가장 치명적 | 자녀 원격 설정 지원 플로우의 완료율 측정 |
| Play 정책 심사 거절 | 배포 자체가 막힘 | 접근성 목적 소명 문서 사전 준비, 정책 담당 사전 문의 |
| 사용자가 AI의 자동 실행을 신뢰하지 않음 | 채택 저하 | 되묻기·구두 동의 UX의 신뢰도 A/B 테스트. 확인 문장에 상대방·금액을 넣는 것과 안 넣는 것 비교 |
| 앱 업데이트 대응 비용 | 운영비 증가 | UI Tree 기반 구조의 실제 내성 측정 — 앱 개편 전후 성공률 비교 |
| 작업당 LLM 원가가 구독료를 초과 | 마진 붕괴 | 작업당 평균 콜 수와 캐시 적중률 모니터링. 단순 반복 작업은 캐시된 경로로 처리하는 최적화 검토 |
| 어르신이 음성 진입 자체를 어려워함 | 제품 사용 실패 | 큰 마이크 버튼 + 인식 결과 대형 표시. 자녀가 초기 설정을 지원 |
| 프라이버시 우려 (대화 내용 노출) | 채택 저하, 규제 리스크 | 비영속화·마스킹 정책을 제품 화면에서 명시적으로 보여주는 것이 오히려 신뢰 장치가 되는지 검증 |

# 9. 해커톤에서 BM 발표 범위

| **추천** 상용화를 강하게 주장하기보다, **"구매자는 자녀다"**라는 고객 구조의 발견과, **"되돌릴 수 없는 행동만 동의를 받는다"**는 안전 경계가 신뢰 기반 BM의 전제라는 점을 함께 제시하는 것이 설득력이 높다. 통신사·제조사 채널은 장기 경로로만 언급한다. |

# 참고 자료

**[S1] AI 스마트폰 도우미 - Google Play**
https://play.google.com/store/apps/details?id=ai.fluiz.ditestbed_agent
고령자 대상 접근성 앱으로, 음성 요청 후 Android Accessibility Service를 이용해 화면을 읽고 버튼 클릭·텍스트 입력·화면 이동을 수행한다고 설명.

**[S2] Gemini Live - Android Help**
https://support.google.com/gemini/answer/15274899
Android에서 화면 공유를 켜고 다른 앱을 사용하면서 Live 대화를 계속할 수 있음. 화면에 대한 실시간 도움을 제공.

**[S3] 손주도움 - Google Play**
https://play.google.com/store/apps/details?id=com.guideops.app
스마트폰 화면·키오스크·약봉투 등을 카메라로 비추면 다음 버튼과 사용법을 음성 안내.

**[S4] Android AccessibilityService API**
https://developer.android.com/reference/android/accessibilityservice/AccessibilityService
접근성 서비스는 UI 이벤트를 받고 활성 창의 UI 트리를 조회할 수 있으며 접근성 오버레이를 그릴 수 있음.

**[S5] Android AccessibilityNodeInfo API**
https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo
UI 노드의 text, contentDescription, boundsInScreen, isEditable, isPassword 등 접근성 정보를 조회하고 ACTION_CLICK·ACTION_SET_TEXT 등을 수행할 수 있음.

**[S6] Google Play AccessibilityService 정책**
https://support.google.com/googleplay/android-developer/answer/10964491?hl=ko
접근성 API 사용 시 선언·공개·동의 요구. 일반 앱의 자율적 계획·실행 자동화는 제한되며 장애 지원이 핵심인 접근성 도구는 별도 기준 적용.

**[S7] Google Play 민감 권한/API 정책**
https://support.google.com/googleplay/android-developer/answer/16558241
Accessibility API는 보안 통제 우회·기만적 UI 조작 등에 사용할 수 없고 목적에 필요한 최소 데이터만 처리해야 함.

**[S8] Android 패키지 가시성 (`<queries>`)**
https://developer.android.com/training/package-visibility
Android 11(API 30) 이상에서는 Manifest에 `<queries>`를 선언하지 않으면 다른 앱의 설치 여부를 조회할 수 없음. AI가 설치된 앱 중에서 대상 앱을 고르는 구조상 필수 선언.

**[S9] 디지털정보격차 실태조사 (과학기술정보통신부·한국지능정보사회진흥원)**
고령층의 디지털 접근·역량·활용 수준을 매년 조사하는 국가승인통계. 발표에서 수치를 인용할 경우 최신 연도 보고서 원문을 직접 확인해 인용할 것.
