# 비즈니스 모델 — 화면 Off 음성 자동조작 에이전트

해커톤 이후 실제 서비스로 확장할 경우의 고객, 과금, 파트너십 가설

UNWORK Hackathon · 2026.08

대표 시나리오: **"엄마한테 사진 보내줘"** — 화면 Off 음성 호출로 카카오톡을 자동 실행해 사진 전송까지 접근성 API로 완료.

# 1. BM 한 줄 요약

| **BM 방향** 초기에는 고령자·디지털 취약계층 대상 B2C로 문제와 사용성을 검증하고, 장기적으로는 통신사·제조사·공공기관 등 "디지털 취약계층 접근성"을 책임지는 주체와 결합하는 B2B2C 모델로 확장한다. |
| --- |

[도식] B2C 검증 → 통신사/제조사/공공 채널 결합 → 접근성 파트너십

> (팀 확인 필요 — 새 시나리오에 맞는 수익 모델 재정의 필요. 이전 버전의 "예매 플랫폼 공식 SDK 결합" 경로는 시나리오 변경으로 무효화되었고, 메신저 사용 자동화에는 대응하는 플랫폼 사업자 과금 경로가 아직 정의되지 않았다.)

# 2. 고객과 사용자 구분

| **구분** | **누구** | **가치** |
| --- | --- | --- |
| 직접 사용자 | 고령자·디지털 취약 사용자 | 화면을 켜고 앱을 조작하지 않아도 사진 전송 같은 일상 작업을 완료 |
| 가족 구매자 | 자녀·보호자 | 반복적인 원격 설명·대리 조작 시간 감소 |
| 기관 고객 | 통신사, 지자체·공공 디지털 포용 사업 | 디지털 취약계층 지원 수단 확보 |
| 제조사 | 스마트폰 제조사 | 시니어 대상 접근성 기능 차별화 |

> (팀 확인 필요 — 이전 버전의 "철도·항공 등 예매 플랫폼 사업자", "자사 예매 앱 운영 기업" 항목은 시나리오와 무관해져 제거함. 이를 대체할 기관 고객 정의가 필요하다.)

# 3. B2C 모델

| **플랜** | **예시 기능** | **가격 가설** |
| --- | --- | --- |
| Free | 월 제한된 자동조작 횟수, 기본 텍스트/음성 안내 | 무료 |
| Family | 무제한 자동조작, 가족 계정 연결, 지원 앱/시나리오 확대 | 월 4,900~9,900원 가설 |
| Priority | (재정의 필요) | 월 9,900~14,900원 가설 |

가격은 검증되지 않은 가설이다. 초기 해커톤에서는 과금보다 "화면 Off 음성 자동조작에 실제로 돈을 낼 의사가 있는지"를 인터뷰로 확인해야 한다.

> (팀 확인 필요 — Priority 플랜의 기존 기능 정의는 "예매 경쟁 시간대 우선 처리·선호 좌석 학습"으로 예매 시나리오에 종속되어 있었으므로 제거함. 가격 구간(9,900~14,900원)만 남겨 두었으며, 이 구간을 정당화할 상위 플랜 기능을 새 시나리오 기준으로 재정의해야 한다. 정의되지 않으면 Free/Family 2단계로 축소하는 것이 정직하다.)

# 4. B2B2C 모델

통신사: 시니어 요금제·디지털 케어 서비스에 번들.

공공기관: 디지털 취약계층의 스마트폰 사용 접근성 지원 사업에 결합.

스마트폰 제조사: 음성 비서 상시 대기 기능에 통합. 단, 이 경로는 Google의 OS 기본 탑재 전략과 정면으로 경쟁한다(8장 리스크 참고).

복지/요양 기관: 고령자 대상 디지털 교육·돌봄 프로그램의 보조 도구.

> (팀 확인 필요 — 이전 버전의 "철도/항공사 공식 SDK 제휴" 경로는 제거함. 메신저 플랫폼 사업자와의 제휴는 근거 없는 가설이므로 기재하지 않았다.)

# 5. 수익원

> (팀 확인 필요 — 새 시나리오에 맞는 수익 모델 재정의 필요. 이전 버전의 "공식 API 연동 SDK — 자동예매 세션 수 과금", "예매 플랫폼당 라이선스" 항목은 예매·결제 수수료 및 예매 플랫폼 제휴에 의존하던 구조여서 전면 제거했다. 사진 전송 같은 일상 조작 자동화에는 건당 과금의 근거가 되는 거래 금액이 존재하지 않으므로, 구독 외의 수익원은 새로 설계해야 한다.)

현재 근거를 갖고 남길 수 있는 항목은 아래 두 가지뿐이다.

| **수익원** | **과금 단위 예시** |
| --- | --- |
| B2C 구독 | 사용자/가족 단위 월 구독 |
| B2B 라이선스 | 통신사·기관 단위 월/연 계약 |

# 6. 비용 구조

LLM/Vision inference 비용: UI Tree만으로 판단 가능한 경우 최소화.

Android 앱 개발 및 QA: OS 버전·제조사·지원 앱별 테스트 비용. 대상 앱(카카오톡) 업데이트 시 UI 변경 대응 비용이 상시 발생.

화면 Off 상시 대기(wake word) 관련 배터리·오탐 튜닝 비용.

보안/개인정보: 데이터 최소화, 감사, 정책 대응. 사진·대화 상대 등 민감 정보를 다루므로 비영속화 원칙 준수 비용이 포함된다.

고객지원/온보딩: Accessibility 권한과 자동조작 범위를 이해시키는 교육 비용.

> (팀 확인 필요 — 이전 버전의 "매크로 탐지 우회 대응 비용"은 예매 시나리오 전용 비용이므로 제거함.)

# 7. 시장 진입 전략

해커톤 데모는 화면 Off 음성 진입 → 카카오톡 자동 실행 → 되묻기 → 사진 전송 완료까지의 단일 플로우를 실기기에서 완주시키는 것에 집중한다.

고령자-자녀 5~10쌍을 대상으로, 자녀가 원격으로 설명하거나 대신 조작하던 시간이 얼마나 줄어드는지 관찰.

되묻기 UX가 실제로 고령자에게 통하는지(질문을 이해하고 답할 수 있는지)를 정성 인터뷰로 검증.

Google Play 접근성 API 정책 준수 범위 안에서만 동작하도록 설계하고, 정책 심사 통과 가능성을 초기에 확인.

정확도와 완수율이 확보된 후 통신사·기관 계약 모델로 확대.

# 8. BM의 가장 큰 리스크

| **리스크** | **영향** | **검증 방법** |
| --- | --- | --- |
| **Google의 OS 기본 탑재** — Gemini Autonomous Task Engine(2026.03)과 Gemini Intelligence(2026.05)가 접근성 기반 멀티스텝 자동화를 Android 기본 기능으로 제공 | 독립 앱의 존재 이유 자체가 흔들림. 유통·전력·모델 접근성 모두 열세 | 화면 Off 진입·되묻기 UX·단일 시나리오 완수율에서 실측 우위를 확보. 기능 커버리지 경쟁은 포기 (`03_Competitive_Differentiation.md` 2·6장 참고) |
| Google Play 접근성 API 정책 심사 | 배포 자체가 막힐 수 있음 | 장애·고령자 지원이 핵심 목적임을 명확히 선언하고 최소 데이터 원칙 준수 |
| 대상 앱(카카오톡) UI 업데이트 | 정확도/성공률 하락, 운영비 증가 | UI Tree 기반 범용성 측정, 실패 시 되묻기로 안전하게 실패 |
| 사용자가 자동 조작을 신뢰하지 않음 | B2C 채택 저하 | 되묻기(확인 질문) UX와 실패 시 복구 흐름 A/B 테스트 |
| 고령자가 음성 진입 자체를 어려워함 | 제품 사용 실패 | 큰 floating button 병행, 자녀가 초기 설정 지원 |
| 사진·대화 상대 등 민감 정보 처리에 대한 거부감 | 권한 승인 단계 이탈 | 비영속화 원칙을 온보딩에서 명시적으로 설명하고 검증 |

# 9. 해커톤에서 BM 발표 범위

| **추천** 해커톤에서는 상용화 수치를 주장하기보다, "화면 Off 음성 진입 + 정보 부족 시 되묻기 + 카카오톡 사진 전송 완수" UX 검증 결과를 보여주고, Google이 같은 방향으로 OS 기본 기능을 내놓고 있다는 사실을 먼저 인정한 뒤 우리가 남는 이유(진입 방식·되묻기·단일 시나리오 깊이)를 제시하는 것이 설득력이 높다. 수익 모델은 확정된 것처럼 말하지 말고 검증 대상 가설로 제시한다. |
