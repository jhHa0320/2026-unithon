# 제품설명서 — 화면 Off 음성 자동예매 에이전트

팀원이 10분 안에 제품의 문제·경험·범위를 이해하기 위한 설명서

UNWORK Hackathon · 2026.08

# 1. 우리가 만드는 것은 무엇인가

| **제품 정의** 화면이 꺼진 상태에서 음성 한마디로 목적 앱을 실행시켜, 목적지·시간·좌석 선택까지 스스로 진행하고 결제 직전에서만 사용자 확인을 받는 Android 음성 자동예매 레이어다. |
| --- |

기존 사용자는 예매를 하려면 화면을 켜고, 앱을 찾고, 출발지·도착지·시간·좌석을 하나씩 눌러야 한다. 예매 경쟁이 치열한 시간대에는 이 과정 자체가 병목이 된다. 우리 제품은 이 조작 과정 전체를 AI가 대신하고, 사람에게는 "결제를 실행할지"라는 최종 판단만 남긴다.

[제품 개념] AI는 목적지부터 좌석까지 실행하고, 사용자는 결제 여부만 판단한다.

# 2. 왜 필요한가

예매 경쟁 시간대에는 화면을 켜고 앱을 여는 몇 초의 지연도 좌석 확보 실패로 이어진다.

고령자는 앱 조작 자체가 부담스러워 자녀에게 예매를 부탁하는 경우가 많다.

자녀 입장에서는 반복적인 대리 예매가 시간 부담으로 누적된다.

기존 튜토리얼·안내형 서비스는 사용자가 직접 화면을 조작해야 한다는 전제가 남아있다.

모든 것을 AI에게 맡기면 결제 책임 문제가 생기므로, 결제 직전 확인 게이트가 필요하다.

# 3. 제품 사용 경험

사용자는 우리 앱을 설치하고 Accessibility 권한과 화면 Off 음성 감지 권한을 명시적으로 허용한다.

화면이 꺼진 상태에서 wake word 뒤 원하는 일을 말한다.

서비스가 코레일+ 앱을 자동 실행한다.

AI가 현재 앱의 UI 구조를 읽고 목적지·시간·좌석까지 스스로 진행한다.

결제 대기 확인 화면이 뜨고 금액·경로·시간을 보여준다.

사용자가 직접 결제 버튼을 눌러야 예매가 완료된다.

[제품 플로우] 목적 발화 한 번으로 결제 대기 화면까지 자동 도달

# 4. 하지 않는 것

| **하지 않는 것** | **이유** |
| --- | --- |
| 결제 버튼 자동 클릭 | 금전 실행은 반드시 사용자 최종 확인이 있어야 함 |
| 사용자 동의 없는 예매 확정 | 결제 대기 화면에서 명시적 확인 없이는 예매가 완료되지 않음 |
| 모든 예매 앱 100% 지원 약속 | 앱별 접근성 구현과 보안 정책이 다름 |
| 상시 전체 화면 저장 | 프라이버시 리스크. 필요한 순간의 최소 UI 정보만 처리 |
| 실 서버 대상 반복 리허설 | 매크로 탐지로 계정이 정지될 수 있음. 데모는 목업 우선 |

# 5. MVP 범위

| **추천 MVP** Android 실기기 + 코레일+ 앱 + KTX 예매 시나리오 1개 + 화면 Off 음성 목표 입력 + Accessibility 기반 자동 진행 + 결제 대기 확인 화면. |
| --- |

| **시나리오 후보** | **추천도** | **이유** |
| --- | --- | --- |
| 서울→부산 KTX 예매 | 높음 | 대표성 있고 목적지·시간·좌석 흐름이 명확함 |
| 반복 이용 노선 예매 | 중간 | 사용자별 선호 좌석 학습 여지 있음 |
| 취소표 실시간 확보 | 낮음 | 매크로 탐지·법적 리스크가 가장 큰 영역, 해커톤 MVP에서 제외 추천 |

# 6. 제품 철학

| **UNWORK 문장** 예매를 더 쉽게 가르치는 것이 아니라, 예매를 위해 화면을 켜고 앱을 조작해야 하는 일 자체를 없앤다. AI에게 맡길 것은 조작이고, 사람에게 남길 것은 결제 여부에 대한 판단이다. |
| --- |

# 7. 제품 이름/메시지 아이디어

"화면을 켤 필요가 없는 예매"

말 한마디로 결제 직전까지 가는 AI

앱을 조작하지 않아도 되는 예매

Wake, then Ready to Pay — AI가 준비하고 사람은 결제만 결정한다.

# 8. 팀이 같은 그림을 갖기 위한 핵심 질문

우리가 없애는 것은 조작인가, 조작에 대한 판단인가? → 조작. 판단(결제 여부)은 남긴다.

사용자가 어떤 순간에 반드시 직접 결정해야 하는가? → 결제 실행.

어떤 상황부터 지원해야 하는가? → 접근성 정보가 잘 노출되고 실 서버 반복 호출 리스크가 낮은 예매 시나리오.

AI가 틀렸을 때 어떻게 안전하게 실패할 것인가? → 낮은 확신이면 진행을 멈추고 사용자에게 확인 요청.

제품 성공은 "AI가 자동으로 다 했다"가 아니라 "사용자가 조작 없이 결제 직전까지 도달했고, 결제는 스스로 확정했다"로 측정한다.

# 참고 자료

**[S1] AI 스마트폰 도우미 - Google Play**
https://play.google.com/store/apps/details?id=ai.fluiz.ditestbed_agent
고령자 대상 접근성 앱으로, 음성 요청 후 Android Accessibility Service를 이용해 화면을 읽고 버튼 클릭·텍스트 입력·화면 이동을 수행한다고 설명.

**[S2] Gemini Live - Android Help**
https://support.google.com/gemini/answer/15274899
Android에서 화면 공유를 켜고 다른 앱을 사용하면서 Live 대화를 계속할 수 있음. 화면에 대한 실시간 도움을 제공.

**[S3] 손주도움 - Google Play**
https://play.google.com/store/apps/details?id=com.guideops.app
스마트폰 화면·키오스크·약봉투 등을 카메라로 비추면 다음 버튼과 사용법을 음성 안내.

**[S4] Android AccessibilityService API**
https://developer.android.com/reference/android/accessibilityservice/AccessibilityService
접근성 서비스는 UI 이벤트를 받고 활성 창의 UI 트리를 조회할 수 있으며 접근성 오버레이를 그릴 수 있음.

**[S5] Android AccessibilityNodeInfo API**
https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo
UI 노드의 text, contentDescription, boundsInScreen 등 접근성 정보를 조회할 수 있음.

**[S6] Google Play AccessibilityService 정책**
https://support.google.com/googleplay/android-developer/answer/10964491?hl=ko
접근성 API 사용 시 선언·공개·동의 요구. 일반 앱의 자율적 계획·실행 자동화는 제한되며 장애 지원이 핵심인 접근성 도구는 별도 기준 적용.

**[S7] Google Play 민감 권한/API 정책**
https://support.google.com/googleplay/android-developer/answer/16558241
Accessibility API는 보안 통제 우회·기만적 UI 조작 등에 사용할 수 없고 목적에 필요한 최소 데이터만 처리해야 함.

**[S8] 코레일 매크로 승차권 불법거래 대응 관련 보도**
매크로 프로그램을 이용한 승차권 부당 확보·재판매는 철도사업법상 단속 대상이며, 코레일은 빅데이터 기반 모니터링과 매크로 탐지 솔루션으로 비정상 접속을 실시간 차단하고 있다고 보도됨.

**[S9] 코레일 매크로 탐지 솔루션 운영 관련 보도**
설·추석 등 예매 성수기에 매크로 탐지 솔루션을 가동해 비정상적 접속 시도 수만 건을 차단한 사례가 보도됨.
