# 제품설명서 — 음성 앱 대행 에이전트

팀원이 10분 안에 제품의 문제·경험·범위를 이해하기 위한 설명서

UNWORK Hackathon · 2026.08

# 1. 우리가 만드는 것은 무엇인가

| **제품 정의** 어르신이 앱 하나만 켜고 말하면, AI가 알맞은 앱을 스스로 찾아 열고 목표를 끝까지 수행하는 Android 접근성 레이어다. 되돌릴 수 없는 행동 직전에만 구두로 동의를 구하고, 동의를 받으면 그 버튼까지 AI가 누른다. |
| --- |

기존 사용자는 무언가를 하려면 먼저 **어떤 앱인지 알아내고, 그 앱을 찾아 열고, 메뉴를 하나씩 눌러야** 한다. 어르신에게는 첫 단계부터 벽이다. 우리 제품은 이 과정 전체를 AI가 대신한다. 사람이 하는 일은 처음 목적을 말하는 것, AI가 정보가 부족해 되물을 때 답하는 것, 되돌릴 수 없는 행동에 "응"이라고 답하는 것뿐이다.

**대상 앱은 고정되어 있지 않다.** 카카오톡은 해커톤 데모 사례일 뿐이며, 앱 이름은 코드 어디에도 없다. 어떤 앱을 열지조차 AI가 설치된 앱 목록을 보고 판단한다.

[제품 개념] AI는 앱 선택부터 목표 완료까지 실행하고, 정보가 부족하면 되묻고, 되돌릴 수 없는 지점에서만 동의를 구한다.

# 2. 왜 필요한가

어르신은 "어떤 앱을 열어야 하는지"부터 막힌다. 아이콘 수십 개 중 무엇이 무엇인지 매칭되지 않는다.

앱을 열어도 메뉴 구조를 몰라 목적지까지 도달하지 못한다. 사진 한 장 보내는 데 5~6단계가 필요하다.

앱이 업데이트되어 UI가 바뀌면 어렵게 외운 순서가 무용지물이 된다.

자녀 입장에서는 같은 작업을 반복 대행하는 시간 부담이 누적된다.

기존 튜토리얼·안내형 서비스는 "사용자가 직접 화면을 조작한다"는 전제가 그대로 남아 있다.

# 3. 제품 사용 경험

사용자는 우리 앱을 설치하고 Accessibility 권한과 마이크 권한을 명시적으로 허용한다. (권한 화면에서 왜 화면을 읽는지, 어디에 쓰는지 먼저 설명한다.)

우리 앱을 열고 큰 마이크 버튼을 눌러 원하는 일을 말한다. 이때 받는 사람·내용 등을 다 말하지 않아도 된다 — 오히려 "카톡 보내줘"처럼 짧게 말하는 경우가 기본이다.

AI가 설치된 앱 중에서 목표에 맞는 앱을 골라 실행한다.

AI가 현재 앱의 UI 구조를 읽고 목표를 향해 스스로 진행한다. 화면이 요구하는데 아직 말하지 않은 정보(받는 사람, 보낼 내용, 어떤 사진 등)가 있으면 AI가 그때그때 음성으로 되묻고, 사용자의 답을 받아 이어서 진행한다.

전송·결제·삭제처럼 되돌릴 수 없는 버튼 차례가 되면 AI가 멈추고 "영희님께 사진을 보낼까요?"라고 구체적으로 확인한다. 사용자가 "응"이라고 답하면 그 버튼을 눌러 실제로 실행한다.

완료되면 AI가 "영희님께 사진을 보냈어요."라고 알린다.

[제품 플로우] 목적 발화 → AI 앱 선택 → (필요시 되묻기 반복) → 구두 동의 → 완료

# 4. 하지 않는 것

| **하지 않는 것** | **이유** |
| --- | --- |
| 특정 앱을 하드코딩해서 그 앱 전용으로 만드는 것 | 앱 이름·버튼 라벨·화면 순서를 코드에 박으면 제품이 아니라 매크로가 된다. 앱 선택조차 AI가 한다 |
| 정보가 불충분한 채로 임의 추측 진행 | 받는 사람·금액·대상이 확인되지 않으면 클릭 대신 되물어서 확인한다 |
| 되돌릴 수 없는 행동을 동의 없이 실행 | 전송·결제·삭제는 오판이 곧 실제 피해다. LLM 판단 + 서버 키워드 게이트로 2단 방어한다 |
| 모든 앱 100% 지원 약속 | 앱별 접근성 구현과 보안 정책이 다름 |
| 상시 전체 화면 저장 | 프라이버시 리스크. 필요한 순간의 최소 UI 정보만 처리하고 추론 직후 폐기 |
| 우리 backend/Android가 PG사 API를 직접 연동하는 별도 결제 구축 | 결제는 대상 앱 자체의 결제 플로우를 accessibility로 그대로 실행하며, 우리 시스템이 결제망에 직접 연결되지는 않는다 |

# 5. MVP 범위

| **추천 MVP** Android 실기기 + 앱 실행 후 음성 목표 입력 + AI 앱 선택(`LAUNCH_APP`) + Accessibility 기반 자동 진행(클릭·텍스트 입력·스크롤) + 정보 부족 시 되묻기(`ASK_USER`) + 되돌릴 수 없는 행동 구두 동의(`CONFIRM_REQUIRED`). 데모 시나리오는 카카오톡 사진 전송 1개. |
| --- |

**데모에서 실제 결제는 하지 않는다.** 카카오톡 "전송" 버튼이 결제 버튼과 코드상 완전히 같은 경로(`CONFIRM_REQUIRED`)를 타므로, 돈을 쓰지 않고도 결제 동의 UX를 그대로 시연할 수 있다.

| **시나리오 후보** | **추천도** | **이유** |
| --- | --- | --- |
| 카카오톡 사진 전송 | 높음 | 어르신이 가장 자주 부탁하는 작업이고, 앱 선택·텍스트 입력·목록 선택·되돌릴 수 없는 행동이 한 흐름에 다 들어간다 |
| 카카오톡 텍스트 메시지 전송 | 높음 | 위와 같은 흐름에서 사진 그리드(접근성 라벨 위험 구간)만 빠져 더 안전하다. **데모 백업 시나리오로 준비할 것** |
| 기차표 예매 + 실제 결제 | 낮음 | 실제 금전 이동, 반복 리허설 시 매크로 탐지 리스크. 데모 이후 확장 시나리오로 |

# 6. 제품 철학

| **UNWORK 문장** 스마트폰 사용법을 더 잘 가르치는 것이 아니라, 앱을 찾아 열고 메뉴를 눌러가는 일 자체를 없앤다. AI에게 맡길 것은 앱 선택과 조작이고, 사람에게 남길 것은 처음 목적을 말하는 것, 되물을 때 답하는 것, 되돌릴 수 없는 순간에 동의하는 것뿐이다. |
| --- |

# 7. 제품 이름/메시지 아이디어

"앱을 찾을 필요가 없는 스마트폰"

말 한마디로 끝나는 심부름

어떤 앱인지 몰라도 됩니다

Say it, done — 말하면, AI가 끝까지 해둔다

# 8. 팀이 같은 그림을 갖기 위한 핵심 질문

우리가 없애는 것은 조작인가, 조작에 대한 판단인가? → 둘 다. 어떤 앱을 열지부터 AI가 판단한다.

사용자가 반드시 직접 개입해야 하는 순간은? → 두 가지뿐이다. AI가 정보 부족으로 되물을 때, 그리고 되돌릴 수 없는 행동에 동의할 때.

왜 전송에도 동의를 받는가? → 전송·결제·삭제는 되돌릴 수 없다는 점에서 같은 종류의 행동이고, 코드상 같은 경로다. 결제만 특별 취급하는 별도 로직을 두지 않는 것이 더 안전하고 더 단순하다.

AI가 틀렸을 때 어떻게 안전하게 실패할 것인가? → confidence가 낮으면 클릭을 강행하지 않고 멈춰서 되묻는다. 되돌릴 수 없는 행동은 LLM이 빠뜨려도 서버가 독립적으로 잡는다.

어떤 앱부터 지원해야 하는가? → 접근성 정보가 잘 노출되고 사용 빈도가 높은 앱. 다만 지원 목록을 코드에 두지는 않는다.

# 참고 자료

**[S1] AI 스마트폰 도우미 - Google Play**
https://play.google.com/store/apps/details?id=ai.fluiz.ditestbed_agent
고령자 대상 접근성 앱으로, 음성 요청 후 Android Accessibility Service를 이용해 화면을 읽고 버튼 클릭·텍스트 입력·화면 이동을 수행한다고 설명.

**[S2] Gemini Live - Android Help**
https://support.google.com/gemini/answer/15274899
Android에서 화면 공유를 켜고 다른 앱을 사용하면서 Live 대화를 계속할 수 있음. 화면에 대한 실시간 도움을 제공.

**[S3] 손주도움 - Google Play**
https://play.google.com/store/apps/details?id=com.guideops.app
스마트폰 화면·키오스크·약봉투 등을 카메라로 비추면 다음 버튼과 사용법을 음성 안내.

**[S4] Android AccessibilityService API**
https://developer.android.com/reference/android/accessibilityservice/AccessibilityService
접근성 서비스는 UI 이벤트를 받고 활성 창의 UI 트리를 조회할 수 있으며 접근성 오버레이를 그릴 수 있음.

**[S5] Android AccessibilityNodeInfo API**
https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo
UI 노드의 text, contentDescription, boundsInScreen, isEditable, isPassword 등 접근성 정보를 조회하고 ACTION_CLICK·ACTION_SET_TEXT 등을 수행할 수 있음.

**[S6] Google Play AccessibilityService 정책**
https://support.google.com/googleplay/android-developer/answer/10964491?hl=ko
접근성 API 사용 시 선언·공개·동의 요구. 일반 앱의 자율적 계획·실행 자동화는 제한되며 장애 지원이 핵심인 접근성 도구는 별도 기준 적용.

**[S7] Google Play 민감 권한/API 정책**
https://support.google.com/googleplay/android-developer/answer/16558241
Accessibility API는 보안 통제 우회·기만적 UI 조작 등에 사용할 수 없고 목적에 필요한 최소 데이터만 처리해야 함.

**[S8] Android 패키지 가시성 (`<queries>`)**
https://developer.android.com/training/package-visibility
Android 11(API 30) 이상에서는 Manifest에 `<queries>`를 선언하지 않으면 다른 앱의 설치 여부를 조회할 수 없음. AI가 설치된 앱 중에서 대상 앱을 고르는 구조상 필수 선언.

**[S9] 디지털정보격차 실태조사 (과학기술정보통신부·한국지능정보사회진흥원)**
고령층의 디지털 접근·역량·활용 수준을 매년 조사하는 국가승인통계. 발표에서 수치를 인용할 경우 최신 연도 보고서 원문을 직접 확인해 인용할 것.
