# 기존 제품 및 차별점 분석

시장에 이미 있는 제품과 겹치는 부분을 인정하고, 우리만의 제품 경계를 명확히 정의

UNWORK Hackathon · 2026.08

# 1. 결론 요약

| **핵심 결론** 화면을 읽고 무엇을 눌러야 할지 알려주는 AI 도우미는 이미 있다. 우리 차별점은 **"어떤 앱을 열지부터 AI가 정하고, 조작을 대행하며, 되돌릴 수 없는 행동에서만 구두 동의를 받는다"**는 자동화 경계에 있다. |
| --- |

[포지셔닝] 전 과정 사용자 조작 ↔ 무제한 자율 실행 사이에서, "되돌릴 수 있는 것은 자동, 되돌릴 수 없는 것만 동의" 영역

# 2. Gemini Live

Gemini Live는 Android에서 화면 공유를 켜면 현재 화면에 대해 실시간으로 대화할 수 있고, Live를 백그라운드로 두고 다른 앱을 사용할 수도 있다. 사용자가 대화로 도움을 요청하고 답을 듣는 경험이 중심이며, **자동으로 UI를 조작하지는 않는다.** 앱을 대신 열어주지도 않는다. 우리 제품은 앱 선택부터 UI 노드 조작까지 실행한다는 점에서 대행 범위가 다르다.

# 3. 손주도움

손주도움은 스마트폰 화면, 키오스크, 가전제품 등을 카메라로 비추면 AI가 다음에 눌러야 할 버튼과 사용 방법을 음성으로 안내한다. 조작은 사용자가 직접 한다. 우리 제품은 안내가 아니라 조작 자체를 실행한다는 점에서 자동화 수준이 다르다.

# 4. AI 스마트폰 도우미 (fluiz)

가장 가까운 경쟁 제품이다. 음성 요청 후 Accessibility Service로 화면을 읽고 버튼 클릭·텍스트 입력·화면 이동을 수행한다고 설명한다. 방향성이 같으므로 **"우리가 세계 최초"라고 주장하면 안 된다.** 우리 차별점은 세 가지로 좁혀야 한다.

| **우리가 다르게 하는 것** | **설명** |
| --- | --- |
| 앱 선택까지 AI가 함 | 사용자가 앱 이름을 정확히 말하지 않아도, 설치된 앱 목록에서 LLM이 대상 앱을 고르고 실행한다 |
| 되돌릴 수 없는 행동의 명시적 경계 | 결제·전송·삭제를 하나의 게이트(`CONFIRM_REQUIRED`)로 통합하고, LLM 판단과 서버 키워드 검사로 2단 방어한다. "어디까지 맡길 것인가"에 대한 답이 제품에 코드로 박혀 있다 |
| 불확실하면 진행 대신 질문 | confidence 임계값 미만이면 서버가 클릭을 막고 되묻기로 전환한다. 추측해서 누르는 것보다 한 번 더 묻는 것이 낫다는 원칙 |

# 5. 차별점의 강도 평가

| **차별점 후보** | **강도** | **설명** |
| --- | --- | --- |
| 되돌릴 수 없는 행동만 구두 동의하는 경계 설계 | 강 | 경쟁 제품들은 "어디까지 자동화할지"의 기준이 불명확하다. 우리는 그 기준이 스키마와 서버 게이트로 구현되어 있다 |
| AI가 앱을 골라 실행 | 중~강 | 어르신의 첫 번째 장벽을 없앤다. 다만 `<queries>` 선언·패키지 가시성 등 구현 난이도가 있다 |
| 정보 부족 시에만 되묻는 최소 개입 | 중~강 | 확실한 정보만으로 클릭하고, 불확실하면 진행 대신 확인 질문으로 전환 |
| 앱 비종속 (특정 앱 하드코딩 없음) | 중~강 | 데모는 카카오톡이지만 코드에 앱 이름이 없다. 확장성 주장의 근거가 되지만 심사에서 실증하기 어렵다 — 데모 중 다른 앱으로 한 번 더 보여주는 것이 가장 강력한 증명 |
| UI Tree 우선 + Vision fallback | 중 | 정확도·비용·속도 측면의 구현 차별화 |
| 화면 Off wake word 진입 | (로드맵) | 제품 비전에는 남아 있으나 이번 데모 범위 밖. **데모에 없는 것을 있는 것처럼 말하지 말 것** |

# 6. 발표에서 피해야 할 주장

**"우리 PG/결제망과 직접 연동돼 있다"** → 사실과 다름. 대상 앱 자체의 결제 화면을 accessibility로 자동 클릭할 뿐, 우리 시스템이 별도 PG 연동을 갖고 있지 않다.

**"화면 Off에서 wake word로 됩니다"** → 이번 데모에 없다. 로드맵으로만 말한다.

**"모든 앱에서 다 된다"** → 접근성 정보·보안 정책 차이 때문에 과장. "앱을 하드코딩하지 않는 구조"와 "모든 앱에서 동작"은 다른 말이다.

**"이런 건 처음이다"** → fluiz 기반 제품이 이미 유사한 방향으로 존재한다. 차별점을 §4의 세 가지로 좁혀 말한다.

**"매크로가 아니다"** → 기술적으로는 반복 자동 조작과 유사한 패턴이다. 개인 사용 목적, 접근성 지원 목적, 되묻기·동의 안전장치로 차별점을 설명해야 한다.

**"플러그인"** → 모바일 OS 차원에서 일반적인 플러그인 개념은 아니다. "Android 접근성 기반 음성 대행 레이어"가 정확하다.

# 7. 추천 포지셔닝

| **추천 문장** 기존 GUI Agent는 어디까지 자동화할지 경계가 불명확하다. 우리는 "되돌릴 수 있는 일은 알아서, 되돌릴 수 없는 일은 물어보고"라는 단 하나의 원칙으로 그 경계를 코드에 박았다. 그 앞뒤의 앱 탐색·조작 노동은 전부 없앤다. |
| --- |

# 8. 방어 가능한 제품 경계

앱 개발사의 별도 연동 없이 Android 접근성 계층에서 동작하는 것을 목표로 한다.

특정 앱을 하드코딩하지 않는다 — 앱 이름·버튼 라벨·화면 순서가 코드에 없다. 대상 앱 선택조차 LLM이 한다.

우리 시스템이 PG사 API를 직접 호출하는 별도 결제 연동을 갖지 않는다 — 대상 앱 자체의 결제 플로우를 접근성으로 조작할 뿐이다.

되돌릴 수 없는 행동은 LLM 판단(1차)과 서버 키워드 게이트(2차)로 이중 방어한다. 안전을 프롬프트 하나에 걸지 않는다.

화면 데이터를 저장하지 않는다 — 추론 직후 폐기하고, 로그에 text/contentDescription 원문을 남기지 않으며, 비밀번호 필드와 주민번호·카드번호 패턴은 서버단에서 마스킹한다.

확신이 낮은 경우 자동 실행 대신 "추가 질문(되묻기)"이나 "지원 불가"로 안전하게 실패한다.

**[S1] AI 스마트폰 도우미 - Google Play**
https://play.google.com/store/apps/details?id=ai.fluiz.ditestbed_agent
고령자 대상 접근성 앱으로, 음성 요청 후 Android Accessibility Service를 이용해 화면을 읽고 버튼 클릭·텍스트 입력·화면 이동을 수행한다고 설명.

**[S2] Gemini Live - Android Help**
https://support.google.com/gemini/answer/15274899
Android에서 화면 공유를 켜고 다른 앱을 사용하면서 Live 대화를 계속할 수 있음. 화면에 대한 실시간 도움을 제공.

**[S3] 손주도움 - Google Play**
https://play.google.com/store/apps/details?id=com.guideops.app
스마트폰 화면·키오스크·약봉투 등을 카메라로 비추면 다음 버튼과 사용법을 음성 안내.

**[S4] Android AccessibilityService API**
https://developer.android.com/reference/android/accessibilityservice/AccessibilityService
접근성 서비스는 UI 이벤트를 받고 활성 창의 UI 트리를 조회할 수 있으며 접근성 오버레이를 그릴 수 있음.

**[S5] Android AccessibilityNodeInfo API**
https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo
UI 노드의 text, contentDescription, boundsInScreen, isEditable, isPassword 등 접근성 정보를 조회하고 ACTION_CLICK·ACTION_SET_TEXT 등을 수행할 수 있음.

**[S6] Google Play AccessibilityService 정책**
https://support.google.com/googleplay/android-developer/answer/10964491?hl=ko
접근성 API 사용 시 선언·공개·동의 요구. 일반 앱의 자율적 계획·실행 자동화는 제한되며 장애 지원이 핵심인 접근성 도구는 별도 기준 적용.

**[S7] Google Play 민감 권한/API 정책**
https://support.google.com/googleplay/android-developer/answer/16558241
Accessibility API는 보안 통제 우회·기만적 UI 조작 등에 사용할 수 없고 목적에 필요한 최소 데이터만 처리해야 함.

**[S8] Android 패키지 가시성 (`<queries>`)**
https://developer.android.com/training/package-visibility
Android 11(API 30) 이상에서는 Manifest에 `<queries>`를 선언하지 않으면 다른 앱의 설치 여부를 조회할 수 없음. AI가 설치된 앱 중에서 대상 앱을 고르는 구조상 필수 선언.

**[S9] 디지털정보격차 실태조사 (과학기술정보통신부·한국지능정보사회진흥원)**
고령층의 디지털 접근·역량·활용 수준을 매년 조사하는 국가승인통계. 발표에서 수치를 인용할 경우 최신 연도 보고서 원문을 직접 확인해 인용할 것.
